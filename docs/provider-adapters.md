# Provider adapters

The Rust runner supports `kind: mock`, `kind: openai_compatible`, and `kind: ollama`. A mock fixture is a JSON object keyed by case ID (or `default`), with `content`, optional `tool_calls`, `latency_ms`, `cost_usd`, `retry_after_ms`, and usage metadata. Mock execution performs no network requests.

The OpenAI-compatible adapter posts non-streaming chat-completion requests. Configure `base_url`, `model`, and optionally `api_key_env`, `timeout_ms`, `temperature`, `top_p`, and `max_output_tokens`. Tool definitions and a case JSON Schema are passed when present; unsupported endpoint features surface as provider errors. `base_url` must be explicit. Loopback HTTP is allowed for local servers; remote endpoints require HTTPS. Credentials are read from the selected environment variable and are not written to result files. HTTP error bodies and request/response headers are not exported. Token usage is recorded when returned; API cost is unknown unless a trustworthy cost is supplied, so a required cost check is inconclusive.

The optional Python JSON Lines process and non-streaming Ollama client are provided under `python/fallbackcontract_adapters`. Install with `python -m pip install ./python/fallbackcontract_adapters`; when a contract selects `kind: ollama`, the Rust runner launches `python3 -m fallbackcontract_adapters.protocol` and uses its versioned JSONL handshake. Configure an explicit local `base_url` and existing `model`; the adapter restricts Ollama URLs to loopback and never pulls models. Ollama accepts JSON mode/schema and tools where the selected local model supports them; the adapter sends non-streaming chat requests and normalizes returned content and usage ([Ollama API documentation](https://github.com/ollama/ollama/blob/main/docs/api.md)). Install the package into the same Python environment used by the CLI. A gateway adapter can map provider events into fixtures or the normalized run protocol without allowing proposed tools to execute.

Provider `capabilities` may be declared per model in the contract. Declarations are treated as user-supplied metadata; the runner does not infer model capabilities from adapter kind or model ID. Cases can list `requires_capabilities`; an explicit false declaration fails that critical compatibility check, while a missing declaration makes it inconclusive. There is no model discovery endpoint or preflight capability matrix, and request-level rejection is still reported by the selected endpoint.
